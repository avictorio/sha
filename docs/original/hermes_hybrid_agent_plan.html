Architecture plan · Hermes-first

A Muse-style agent, built on Hermes, running hybrid: local first, cloud on demand.

Hermes Agent (Nous Research) already ships the runtime, the learning loop, memory, skills, subagents, cron, the multi-platform gateway, and MCP — so the plan is mostly configuration, with exactly one major custom build: the phone-calling tool. Local Ollama models handle everyday and private work on the Legion Pro 7i, docked and always-on; a cloud model steps in only when a task earns it.

What Hermes hands you

From the official Hermes feature set — install and configure, no code.
  • Persistent agent runtime — runs on a $5 VPS, a GPU box, or serverless (Daytona, Modal); 7 terminal backends: local, Docker, SSH, Daytona, Singularity, Modal, Vercel Sandbox
  • Closed learning loop — agent-curated memory, autonomous skill creation, skills that self-improve during use
  • Cross-session recall — FTS5 search with LLM summarization, plus Honcho dialectic user modeling
  • Subagents & delegation — spawn isolated subagents for parallel workstreams
  • Built-in cron — scheduled automations delivered to any connected platform
  • MCP support — connect to any MCP server for tools and data sources
  • Full web control — search, extract, browse, vision, image generation, TTS
  • Model-agnostic — Nous Portal, OpenRouter, OpenAI, Anthropic, or any compatible endpoint — the hybrid routing below rides on this

What you still build

The honest gap list. This is where the entire custom budget goes — nothing else.
  • The phone tool — PSTN dialing is not built in. A telephony plugin or provider integration, a call-brief format, and transcript return into memory (§06)
  • Routing policy — Hermes can switch models; the rules for when a task may leave the machine are yours to write (§03)
  • Approval & vault layer — per-action approvals, credential injection, and an OTP flow, layered over Hermes' native command approval (§07)
  • Browser profile isolation — a dedicated Chrome profile for the agent, so its logged-in life is not your logged-in life (§05)
  • Always-on operations — service supervision, update discipline, and backups of the Hermes home directory (§04)
02

How you talk to it

The interface is a product decision, not a framework feature. Three real options — chat, web, native — and this plan picks deliberately.

Everything you do with the agent travels through this layer: asking it things, receiving the morning brief, approving a phone call before it dials (§06), reviewing what it did while you were out. In the stack above it's a single line — "Channels & gateway" — but it decides how the whole system feels day to day, so it gets its own section. In short: chat is the only option that costs zero build, because Hermes' gateway already speaks to the messaging apps on your phone. Web and native are real surfaces you'd design, build, and maintain yourself — worth it later, for specific jobs, not as the front door.

The pick · MVP

Chat integration

What it is: you talk to the agent inside a messaging app you already have. Hermes' gateway connects 20+ platforms from one process — Telegram, Discord, Slack, WhatsApp, Signal, Matrix, email, SMS, Teams, and more.

  • Zero build — connect the gateway, hold your first conversation the same day (Day 2 of the sprint)
  • Push is free — cron briefs and alerts arrive as messages, with notifications the platform already handles
  • Approvals are a tap in the same thread you chat in (§07) — no separate app to open
  • Voice notes work via Hermes' voice mode on supported platforms
  • The limit: chat is a narrow pipe — attachments and links, yes; dashboards, big tables, and searching months of history, no
Later · light build

Web app

What it is: a browser-based console served from the local box and reached over Tailscale (§04) — chat view plus the screens chat can't do. Hermes gives you the agent and its APIs; the web surface itself is yours to build.

  • Best for review — activity logs, call transcripts, escalation history, memory and skills you can browse and edit
  • Richest approvals — a queue with diffs and context, instead of one tap per message
  • Runs anywhere — any browser, no install, no app store; one codebase
  • The costs: weeks of build, auth to get right, and push needs Web Push plumbing before a brief can actually reach you
Deferred · full build

Native app

What it is: a purpose-built iOS / Android (or desktop) client talking to your Hermes box. The most polished option — and the only one where you build everything: Hermes ships no native client.

  • Best feel — native push, biometric approve, share sheet, widgets, offline shell
  • Muse-grade approval cards live here — this is the surface §07 deliberately doesn't replicate in the MVP
  • The costs: two platforms or a cross-platform compromise, store review, signing, and a permanent maintenance tail
  • Same agent underneath — a native app adds polish, not capability; every feature still comes from Hermes

Which surface wins the moment? — pick a moment

Within chat, the platforms are not interchangeable. The gateway makes switching cheap, but each platform shapes what the agent can do:

Telegram — the MVP channel

Bots are first-class citizens: fast setup, reliable push, inline buttons for approval taps, generous file handling, and voice messages for Hermes' voice mode. It's the quickest route from install to a working agent — which is why Phase 0 and Day 2 of the sprint are built around it.

WhatsApp — where people already live

The strongest reason to switch later: zero new-app friction, for you or for family the agent might message. The friction is on the platform side — bot access runs through more restrictive API arrangements than Telegram's, with tighter rules on proactive, agent-initiated messages. A real option, a worse first one.

Slack & Discord — the work & community shapes

Threads, channels, and rich formatting make Slack a natural fit if the agent's work is work — briefs in a channel, approvals in a thread. It also welds your personal agent to a work identity and a company workspace's retention rules. Discord is the same shape with a community accent. Both are one gateway config away, neither is the default.

Email & SMS — the universal fallback

Reach anyone, on anything, forever — at the cost of everything else: slow, unstructured, no approval buttons, no presence. Keep them connected as the delivery path of last resort (and for people the agent contacts who aren't on anything else), not as how you talk to it.

The pick: chat-first, web-second, native-when-earned

MVP: Telegram, doing triple duty — conversation, cron delivery, and approval taps (§07). Later: a small web console when review volume earns it — transcripts, logs, and memory are the screens that justify it, not chat. Native: only if the hybrid proves itself and the polish is worth a second product to maintain; §07 already defers Muse-style app approval cards to exactly that moment. And because the gateway serves every platform from one process, changing your mind is cheap: swapping the primary channel from Telegram to WhatsApp is a configuration change, not a rebuild — the agent, its memory, and its skills don't care which window you talk through.

Nothing leaves the machine

Never sent to the cloud

  • Anything tagged private — journal, messages, personal notes
  • Health and financial detail — statements, records, balances in context
  • Credentials and one-time codes — never shown to any model; the vault injects them at the tool layer (§07)
  • Anything at all while local-only mode is on — one toggle in the gateway, no exceptions, no silent fallback

What earns a cloud escalation

  • The local model fails the same step twice — retry budget exhausted, router escalates with the failure context
  • The task is long-horizon multi-step — bookings, research, anything with 10+ dependent tool calls
  • The working set exceeds the local context — even at 64K, big repo or document jobs go up
  • You say so — an explicit "use the big model" always wins, and is logged

The two local-model requirements are non-negotiable. First, the model must support tool calling — without it Hermes can chat but cannot act: no file edits, no terminal, no browsing. Second, context: Ollama defaults to a 2,048-token window, and Hermes requires at least 64,000 tokens for agentic work. Raising num_ctx is the single most important setting in this whole plan.

On the Legion Pro 7i (§04) the local side runs in two tiers: a 7B–14B tool-calling model fully in the 12 GB VRAM for quick lookups and everyday work, and a 27B–32B Q4 tool-calling model with partial offload into system RAM as the local default for serious work — both from a tool-calling family such as Qwen. A frontier cloud model (via OpenRouter or direct) is reserved for escalations, and 70B-class models belong to that cloud tier, not to this machine.

# Ollama: give the local model an agent-sized window
# (Modelfile for a custom local default)
FROM qwen3:32b
PARAMETER num_ctx 65536

# or, host-wide via the Ollama service environment:
OLLAMA_CONTEXT_LENGTH=65536
OLLAMA_KEEP_ALIVE=30m   # stay warm between cron runs

Schematic — the exact keys live in your Hermes/Ollama config; the values (64K floor, warm model) are the decisions that matter.

04

Hosting: the Legion Pro 7i

The host is the Lenovo Legion Pro 7i — docked, plugged in, and awake on the home network.

The host is the Lenovo Legion Pro 7i: 16″ WQHD IPS 240Hz display, Intel Core i9-13900HX (24 cores), GeForce RTX 4080 Laptop at 175W with 12 GB VRAM, 64 GB DDR5 RAM, 2 TB + 2 TB SSD (4 TB total), running Windows 11 Home. On this machine Hermes uses the Docker terminal backend — agent commands execute in a container, while the Hermes home directory (~/.hermes: memory, skills, sessions, config) persists on the host as a mounted volume. Ollama runs on the CUDA path, the supported route for NVIDIA hardware: the GPU does the inference work, with no translation layer or workaround in between.

The specs clear the bar this design sets with room to spare — double the 32 GB RAM floor for 27B-class local models, a full-power CUDA GPU, and storage for models, Docker images, and years of logs. The constraints on this host are about form factor, not power, and they are covered in the table below.

The host

Lenovo Legion Pro 7i

Fast tier · local

7B–14B, fully in VRAM

Everyday & quick work

Tool-calling models in the 7B–14B range run entirely inside the 12 GB VRAM — nothing spills to system RAM, and responses feel instant. This tier handles quick lookups, the morning brief, summaries, drafts, and routine multi-step tasks. It is the default the router in §03 reaches for first.

Big tier · local

27B–32B Q4, partial offload

Serious local reasoning

Tool-calling models in the 27B–32B range at Q4 quantization run with partial offload into the 64 GB of system RAM — slower than the fast tier, at reading pace, and entirely usable for background and multi-step work. 70B stays off this machine: it can be coaxed into RAM offload, but slowly enough that cloud fallback wins every time. Beyond the big tier, the router escalates to cloud (§03) — that is what the hybrid design is for.

05

Browser: local Chrome first

Hermes offers Browserbase, Browser Use cloud, local Chrome via CDP, or local Chromium. Local CDP is the primary here.

Primary — local Chrome via CDP

The agent drives a real Chrome on the host box, over the DevTools protocol.
  • Real profile, residential IP — sites see a normal browser on a home connection, not a datacenter cloud browser; far fewer bot walls
  • Takeover is trivial — the browser is on a screen you own; when the agent stalls, you look at the same window and unstick it
  • Sessions persist — logins survive between tasks because the profile lives on the box, like Muse's leased Chromium profile

Fallback — cloud browser backend

Browserbase or Browser Use cloud, for when local is the wrong tool.
  • Parallel subagent browsing — five research subagents can't share one local Chrome window gracefully; cloud sessions fan out
  • Throwaway sessions — one-off, no-login tasks that shouldn't touch the persistent profile at all
  • Known fragility stays — login-heavy flows, OTPs, and CAPTCHAs are backend-dependent everywhere; no backend choice makes them solved

The one rule that matters: a dedicated agent profile

Locally, the browser's strength is also its risk — that profile is a logged-in life. So the agent gets its own Chrome profile and its own accounts where practical, signed into the services it works with (email, calendar, booking sites), and never your daily profile. When a site demands a one-time code, the flow is: agent pauses → the code is fetched through the protected approval path (§07) → agent resumes. The agent never sees a password; the vault injects credentials at login prompts, and 2FA stays a human-approved step, not an automated one.

06

Phone: the one real build

Hermes' voice mode is real-time voice in chat apps — not dialing a business on the PSTN. Telephony is a layer you add.

Two proven ways to give Hermes a phone number. The plan starts with the Plivo plugin — it is a published Hermes plugin (hermes-plivo-phone-gateway on PyPI) that adds inbound and outbound calling directly — and keeps Twilio + Vapi as the step-up if call quality or voice naturalness becomes the bottleneck. Either way, the design around the call is yours, and it's the part that matters most:

STEP 1
Draft the call

The agent prepares a brief: who, which number, the goal, the exact opening line, what it may agree to, and what it must not.

STEP 2 — THE GATE
You approve

Nothing dials until you see the brief and approve it — the same pattern proven in the field: "pause and show me who you plan to call and what you will say."

STEP 3
Call runs

The provider's voice stack talks; the agent works the brief, handles hold music and phone trees, and stays inside its mandate.

STEP 4
Transcript lands

Full transcript + outcome summary are written back into Hermes memory, so the next session — and the morning brief — know the call happened.

Why "local" stops at the phone line

The agent, its memory, even its speech can live entirely on your box — but a phone call must cross a carrier network. PSTN access means Twilio or Plivo, full stop, and inbound calls need a public webhook reaching your machine, which on a home network means a cloudflared tunnel. That's the honest boundary of the hybrid design: local control, cloud carriage — and it's why call audio and transcripts are pulled back into local memory the moment a call ends, rather than left living in a provider dashboard.

07

Approvals & secrets

Hermes ships command approval and container isolation. Muse-style trust needs a policy layer on top.

Three tiers of action

  • Free: read, search, summarize, draft — the agent just does these
  • Notify: sends, bookings under a set spend cap, file changes outside the sandbox — done, then reported in the next brief
  • Approve first: phone calls, payments above the cap, anything irreversible or sent as you to a person who'd notice

Secrets live outside the model

API keys and passwords sit in a local vault / secret store on the box. Tools receive credentials at execution time; prompts never contain them, so neither the local model nor — critically — a cloud escalation ever sees a raw secret. Cloud calls get the task, not the keys.

One-time codes are a protected flow

OTPs are fetched through a dedicated reference path scoped to the active sign-in, shown to you for approval, and never stored. The agent can use a code at a login prompt; it cannot go fishing through your messages for one on its own initiative.

What this deliberately doesn't replicate

Muse's per-action approval cards inside a polished app, its Goals and Feed surfaces, and its proactive-edition cadence are product UI, not agent capability. This plan gets the same safety semantics — nothing consequential happens unapproved — delivered through the gateway you already use (approve from Telegram with a tap). If the hybrid proves itself, a nicer approval surface is a Phase 5 luxury, not an MVP dependency.

The first sprint

Week one, day by day. No orchestrator code is written in this sprint — that is the entire point of the Hermes-first plan.
  1. DAY 1
    Provision the Legion Pro 7i. Dock it and plug it in, OS updates, sleep disabled, Tailscale in, static local IP. Install Ollama as a service on the CUDA path.
  2. DAY 2
    Install Hermes. Docker terminal backend, persistent ~/.hermes volume, gateway connected to Telegram. First conversation: ask it something, watch it use a tool.
  3. DAY 3
    Local model, tuned. Pull the 32B tool-calling model, set num_ctx to 65536, keep-alive on. Verify: multi-step file + terminal task completed fully offline (Wi-Fi off test).
  4. DAY 4
    Cloud fallback + routing policy. OpenRouter key in the vault, escalation rules from §03 written into config, local-only toggle tested. Deliberately break the local model and watch the router escalate — and log it.
  5. DAY 5
    Memory & cron. Seed the user profile, set the morning-brief cron, confirm the learning loop is writing memory and recalling it across sessions (FTS5 check).
  6. DAYS 6–7
    Browser + first connectors. Dedicated Chrome profile via CDP, agent's own logins, 2–3 MCP connectors (email, calendar, files). End of week demo: a real task — research + book nothing, but draft everything — done end to end.

The risk register, honestly

Local model quality is the whole bet. If the 32B local model can't hold a multi-step tool chain together, the router escalates constantly and you've built a cloud agent with extra steps — mitigate by testing the offline task suite on Day 3, before anything depends on it. Always-on is a chore you chose: updates, disk, and backups on a home box are yours now; the nightly ~/.hermes snapshot is not optional. Login-heavy browsing stays fragile on every backend — budget patience for OTP and CAPTCHA flows rather than engineering around them. And the phone build is a real build: the plugin shortens it, but the brief format, the approval gate, and transcript handling are design work, scheduled as their own phase for a reason.
